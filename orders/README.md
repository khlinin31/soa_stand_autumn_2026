# Orders: устройство сервиса

Сервис на Go 1.26, драйвер Postgres `pgx/v5`, без других зависимостей.
Задание 1 и задание 2 решены в одном сервисе.

| Файл | Что в нём |
|---|---|
| `main.go` | запуск, маршруты, фоновые циклы |
| `app.go` | `POST /orders`, `GET /orders/{id}`, HTTP-клиент, паузы повторов |
| `processor.go` | обработка заказа: резерв, оплата, отказ банка; фоновый воркер; сверка списаний |
| `breaker.go` | circuit breaker для Payment |
| `store.go` | схема базы и запросы |
| `events.go` | outbox и публикация `order.paid`; вебхук `delivery.confirmed` и бонусы |

## Оформление заказа

```
POST /orders
  1. INSERT orders (status = pending)            заказ есть в базе раньше, чем о нём узнают соседи
  2. горутина processOrder(id) ─┐                ответ ждёт её не дольше 600 мс
  3. ответ 201 {id, status} ◄───┘ или pending    pending доводит фоновый воркер

processOrder(id)                                 каждый шаг можно повторять
  a. POST /reservations                          Inventory возвращает действующий резерв (200)
  b. POST /payments, Idempotency-Key = id        повтор с тем же ключом не списывает второй раз
       201 / 200  → UPDATE status = paid + INSERT outbox    одна транзакция
       402        → DELETE /reservations/{id} → status = rejected
       500, таймаут, разрыв → заказ остаётся pending, повтор позже
```

Ключ идемпотентности равен id заказа, а тело запроса (`order_id`, сумма,
валюта) у заказа не меняется. Поэтому любое число повторов даёт не больше
одного списания: Payment на повтор возвращает результат первой операции
(`200` с тем же `charge_id` или снова `402`).

Фоновый воркер каждые 200 мс выбирает `pending`-заказы, у которых наступило
`next_attempt_at`, и запускает для них тот же `processOrder`. Пауза между
попытками растёт: 200 мс, 400 мс, 800 мс, затем 2 с, с разбросом ±20 %.
В памяти процесса хранится множество заказов «в работе», чтобы горутина
запроса и воркер не обрабатывали один заказ одновременно. Даже если бы это
случилось, второго списания не будет из-за ключа.

## Защита Payment: circuit breaker

Пока Payment недоступен, заказы не шлют в него запросы, а получают `pending`
сразу. Breaker считает сбои подряд с весами: таймаут 6, разрыв соединения 3,
быстрый ответ `5xx` 1; порог 12. Значит, два таймаута подряд размыкают его
сразу, а случайная серия ответов 500 нет. В разомкнутом состоянии раз в паузу
(1 с, затем 2, 4, 8 с) проходит один пробный запрос. Успех замыкает breaker,
и воркер дооплачивает накопившиеся заказы. Дополнительно не больше 10
запросов к Payment выполняются одновременно.

Таймаут запроса на оплату 5 с и растёт с номером попытки до 15 с: медленный,
но живой Payment успевает ответить.

## Потерянный ответ

Если соединение оборвалось без ответа, списание могло пройти. Сервис сразу
сверяется через `GET /payments?order_id=`: есть списание, значит заказ
`paid`. Если сверка не удалась, срабатывает обычный повтор с тем же ключом,
который вернёт `200` и ту же операцию.

## Событие order.paid (задание 2): transactional outbox

Смена статуса на `paid` и вставка строки в `outbox` идут в одной транзакции.
Отдельный цикл публикует строки без `published_at` в `POST /events` и
отмечает их после ответа `202`. Неудача: повтор с паузой до 5 с.

* Упал после записи в базу, до публикации: строка в outbox осталась,
  после рестарта событие уйдёт.
* Упал после публикации, до отметки: событие уйдёт ещё раз с тем же `id`
  (`order-paid-<id заказа>`). Подписчик отличит копию по `id`.
* Событие для неоплаченного заказа невозможно: строка в outbox появляется
  только вместе со статусом `paid`.

При старте процесса все `pending`-заказы и неопубликованные события берутся
в работу немедленно. Заказ, который был в оплате в момент `kill -9`,
повторяет запрос с тем же ключом, получает `200` и становится `paid`.

## Бонусы (задание 2): inbox

`POST /webhooks/delivery` в одной транзакции:

```sql
INSERT INTO inbox (event_id, user_id, bonus_points) ... ON CONFLICT (event_id) DO NOTHING;
-- строка вставилась → событие новое:
INSERT INTO bonus_balances ... ON CONFLICT (user_id) DO UPDATE SET points = points + EXCLUDED.points;
```

Одновременные копии одного события: вторая вставка ждёт на первичном ключе,
пока завершится первая транзакция, и получает конфликт. Падение до `COMMIT`
откатывает всё, шина не получает `2xx` и присылает событие снова. На копию
уже обработанного события ответ тоже `200`.

## Что будет при отказе

| Вызов | Ошибка 5xx | Нет ответа | Ответ потерян |
|---|---|---|---|
| Inventory `POST /reservations` | заказ `pending`, повтор | то же, таймаут 3 с | повтор вернёт действующий резерв (200) |
| Inventory `DELETE /reservations/{id}` | заказ `pending`, повтор снятия | то же | повтор отвечает 204 |
| Payment `POST /payments` | повтор с тем же ключом, breaker +1 | таймаут, breaker +6, `pending` | сверка `GET /payments`, затем повтор с ключом |
| Шина `POST /events` | повтор с паузой | таймаут 2 с, повтор | копия с тем же `id` |
| Входящий `delivery.confirmed` | ответ 503 при ошибке базы, шина повторит | | копия даёт конфликт в inbox, бонусов не прибавится |

Цена решения: ответ на заказ может быть `pending`, и итог виден только через
`GET /orders/{id}`; лишние запросы при повторах (пробные запросы breaker'а,
сверки); больше кода и таблиц. Что может сломаться: если упадёт сама база,
сервис не примет заказ (ответ 503), потому что без записи заказа обещать
покупателю нечего.

## Что растёт в базе

* `outbox`: опубликованные строки не нужны. Их можно удалять фоновой
  задачей, например старше суток.
* `inbox`: id обработанных событий. Хранить нужно столько, сколько шина
  может прислать копию (окно повторной доставки), затем удалять.
* `orders`: история заказов, растёт по бизнес-смыслу; архив или партиции по
  дате.
